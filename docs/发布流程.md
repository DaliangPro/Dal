# Dal 发布流程

## 已确定的默认路线

单人维护，在维护者 Mac 上复用 `Muse Local` 证书签名，通过 GitHub Release 分发 DMG 和 SHA256 校验文件。不导出证书私钥，不要求第二位审核人，不做 Apple 公证。自动更新保持关闭，默认安装包不捆绑本地 ASR 服务和模型。下载者可能遇到 macOS 安全提示，发布说明必须明确这些边界。

`release-verify.yml` 默认只展示本机入口。它的 `notarized` 选项保留完整 Developer ID、公证、Cloud/Local 和真机更新回滚检查，只有将来另行配置凭据并验收后才使用。

## 一次发布的入口

先准备新版本的中文发布说明及真实验收记录并提交到仓库。验收记录说明实际测试的软件版本、源码或候选、日期、场景、结果和未验证项。至少覆盖本次改动及录音、直出、润色、取消和无输入框复制；相关功能没有测试通过时先修复，不填写虚构的通过结论。本机手动分发不要求证明仍关闭的自动更新功能已通过。

维护者明确要求发布后，在干净的 `main` 分支运行（版本和文件名换成本次值）：

```bash
python3 scripts/publish-release.py \
  --version 2.1.2 --build 1 \
  --notes docs/2026-10-18-Dal-v2.1.2-发布说明.md \
  --smoke-record build/2.1.2-真机验收.md \
  --merge-pr 13
```

这里的 `2.1.2`、PR `13` 和文件名是示例，不是已经完成的验收或发布。源码已合并时省略 `--merge-pr`。版本号必须高于已公开版本。修复版本一般增加最后一位，功能大版本另行确定。

入口按顺序执行：

1. 检查仓库、工作区和 `main`；有 PR 时等待该 PR 的同一提交 CI，通过后按固定提交合并。
2. 更新本机 `main`，锁定其源码；等待该提交的 `push` CI 成功。失败、取消、缺失和超时均不跳过。
3. 检查本机证书，构建 DMG；挂载后核对版本、Build、Bundle、来源提交和严格签名，计算 SHA256。
4. 保存候选状态到 `dist/manual-release/<版本>/`，创建 GitHub 草稿并上传安装包和校验文件。
5. 核对 GitHub 附件名称、大小和服务端 SHA256 与本机候选一致；正常时无需下载。服务端校验信息缺失或异常时，才下载并核对本机指纹、挂载内容和签名。公开前复核 `main` 未变化及 CI 通过，之后才公开 Release。
6. 自动创建仅更新 `updates.json.latest` 的清单 PR，等待它的 CI 后合并。自动更新制品列表保持为空。

默认入口不会重启正在使用的 Dal，也不会触碰正式用户词库。若要求本机安装，发布结束后另用现有部署入口完成。发布后的清单提交不修改应用功能，因此 Release 标签仍指向生成安装包时的准确源码。

## 失败与续跑

用完全相同的命令重试。构建失败会保留诊断目录并重新构建；已验证候选会复用；已有本次草稿会先核对服务端指纹再继续。不会删除已有公开版本、强推标签、覆盖未知草稿或绕过 CI。

若公开成功、清单 PR 尚未通过，再执行同一命令会验证已发布附件并继续清单同步，不重复发布。有本机原始候选时，核对其签名及服务端指纹；本机候选记录缺失时才下载复验。公开版本始终按原始来源提交核对，允许清单合并后 `main` 已前进。尚未公开时，版本、源码、Build、说明或验收记录变化不会接管旧候选；先检查变化，保留旧目录后重新准备。创建草稿的网络结果不明时，先读取同名版本判断归属再继续，不盲目重传。

需要主动下载、挂载及严格验签时，可显式复验已有公开版本，不修改 GitHub、不生成新版本：

```bash
python3 scripts/publish-release.py --version 2.1.1 --verify-existing
```

代理执行过程中创建的每个 PR 都应附到当前聊天；交付应给出 Release 链接、实际 CI 结果和附件校验结果；触发下载回退时说明复验结果。不把入口提示作业成功说成发布成功，不把本地测试通过说成 GitHub CI 通过。
